State of the design, deliberately chosen: import-per-call is rejected because the FIRST ingest would pay module resolution + native binary load inside the A-06 / T-01-08 5-second budget, and a bare cached promise without the rejection-reset would poison every subsequent ingest forever after one transient load failure; the memoized-with-reset singleton shares one in-flight attempt across concurrent ingests (no import storm) while allowing a retry after a failed load.
3. In `hardenImage`, keep the exact order of operations: `sniffImage` first (returns the unchanged 400 'neither PNG nor WebP' message before sharp is ever touched), then the Buffer normalisation, then `const sharp = await loadSharp()` placed OUTSIDE the existing codec `try` block, then the existing try body unchanged: `sharp(buf, { limitInputPixels: MAX_IMAGE_PIXELS, failOn: 'warning' }).timeout({ seconds: HARDEN_TIMEOUT_SECONDS })`, the `ext === 'png' ? pipeline.png() : pipeline.webp()` branch, and the existing catch returning `codecMessage(err)`. `codecMessage()` and the client-facing string prefix it produces must remain byte-identical (nothing else in the repo produces that string today — grep confirmed).
4. Load-failure semantics: because `await loadSharp()` sits outside the codec catch, a missing native binary / `ERR_MODULE_NOT_FOUND` propagates out of `hardenImage`, out of the un-caught Stage 5 call site (incidents.ts:262), into `app.ts` `setErrorHandler`, which logs the real error server-side and answers `{statusCode: 500, error: 'Internal Server Error', message: 'internal server error'}`. This is intentional: a broken sharp install is an OPERATIONAL failure, so it is a 500 + server log, never a 400 that blames the client — and it keeps loader internals (absolute filesystem paths) out of client-visible bodies. It also means `apps/api/src/routes/incidents.ts` and `HardenResult` need NO changes: do not edit that file (it is owned by sibling item 261014-m3w in this batch).
