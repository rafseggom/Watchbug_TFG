  <name>Task 1: Wire the TTL purge sweep end-to-end — module, config knob, boot registration</name>
  <files>apps/api/src/purge.ts, apps/api/src/config.ts, apps/api/src/app.ts</files>
  <action>
Create `apps/api/src/purge.ts` and wire it through config → composition root → DB + Storage, proving the whole path on one real sweep.

1. **Config knob** (`apps/api/src/config.ts`): add `purgeIntervalMinutes: number` to `AppConfig` and read it with the existing `readInt(env, 'WATCHBUG_PURGE_INTERVAL_MINUTES', 60)` — the same fail-fast contract every other variable uses (a non-numeric or sub-1 value exits at boot naming the variable, so a `0` can never become a hot-loop interval). The item's file list did not name config.ts; this addition is deliberate: config.ts's own docstring claims ALL server configuration loads through it, so reading `process.env` inside purge.ts would break that contract.

2. **Module shape** (`apps/api/src/purge.ts`): export `startPurge(deps: { db: AppDb; storage: Storage; intervalMinutes: number }): { stop(): void }` with an internal `runPurge(deps)` one-shot sweep. Imports stay to drizzle operators, `./db/schema`, `./db/client` (type), `./ports` (type) — disk access happens exclusively through the injected `storage.delete(...)` port, which is where FsStorage re-validates `STORAGE_KEY_REGEX` and the volume-root prefix.

3. **Identity sweep (RET-01 / R-09):** one set-based `db.update(incidents).set({ userId: null, userName: null, userEmail: null })` where `identity_purge_at <= now` AND at least one of the three identity columns `isNotNull` (an `or(...)` guard), with `.returning({ id })` to count what changed. The guard is the idempotency mechanism: `identity_purge_at` is NOT NULL and remains in the past after a purge, so rows already stripped never match again.

4. **NO SCHEMA CHANGE** — do not touch `apps/api/src/db/schema.ts`. Both purge columns already exist (schema.ts:40-41), which makes any edit there a Drizzle migration and an AGENTS.md consultation trigger. A purge-scan index is deliberately skipped too: the retention bound keeps the table small (rows are deleted at 90 days) and the sweep runs at most once a minute, so an unindexed scan is acceptable here; adding an index would require a reviewed migration for no felt gain.

5. **Artifact sweep (RET-02 / R-10):** `db.select({ id, storageKey }).from(incidents).where(lte(incidents.artifactPurgeAt, new Date())).limit(ARTIFACT_BATCH)` with `ARTIFACT_BATCH = 100` (module constant), then per row, **blob first, row second**: `await storage.delete(row.storageKey)`, and only on success `db.delete(incidents).where(eq(incidents.id, row.id))`. If the blob delete throws, log `[watchbug] purge: artifact blob delete failed (id=<uuid>, kept for retry)` and continue to the next row — the row survives as the pointer and is retried on the next tick. This ordering is mandatory: the WR-03 comment in incidents.ts proves a row deleted while its blob delete failed leaves a rowless blob that a by-row purge can never see again (an unrecoverable leak in the attachments volume), while the reverse failure (row left, blob gone) self-heals because `FsStorage.delete` is `rm(..., { force: true })` and the row delete is retried.

6. **Logging:** after each sweep, when anything was purged, emit one line `[watchbug] purge: identity=<n> artifacts=<n>`; per-row failures include the incident uuid. Counts and uuids only — the `user_*` values being purged must never be interpolated into log output (they are the PII the job exists to destroy).

7. **Resilience:** wrap the entire sweep body in try/catch logging `[watchbug] purge sweep failed: <err>`. `startPurge` fires the boot sweep immediately as a caught, fire-and-forget promise (boot never awaits it — a dead DB cannot fail `buildApp`/`listen`), then `setInterval(sweep, intervalMinutes * 60_000)` with `timer.unref()` (pattern: `ingest/caps.ts:252`), guarded by a closure `running` flag so a slow sweep skips overlapping ticks instead of stacking queries, returning `stop()` → `clearInterval`.

8. **Registration** (`apps/api/src/app.ts`): immediately after `registerIncidentsRoutes(...)`, add `const purge = startPurge({ db, storage, intervalMinutes: config.purgeIntervalMinutes });` and `app.addHook('onClose', async () => purge.stop());` so the timer is cleared when the instance closes (tests, smoke, shutdown).
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| DB → purge job → attachments volume | Rows read from Postgres drive filesystem deletions — a poisoned/incorrect `storage_key` would aim a delete outside the volume if the Storage seam were bypassed |
| Env/operator → interval configuration | `WATCHBUG_PURGE_INTERVAL_MINUTES` reaches the scheduler from deployment config |
| Purge job → api logs | Purge output lands in `docker compose logs api`, alongside the very PII the job destroys |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-m3v-01 | Tampering | `apps/api/src/purge.ts` → `storage.delete` | high | mitigate | The purge reaches disk ONLY through the injected `Storage` port: `storage.delete(row.storageKey)` with the key read from the row itself. `FsStorage.pathFor` re-validates `STORAGE_KEY_REGEX` (no `.` ⇒ `..` impossible) and asserts the resolved path stays under the volume root before `rm`. purge.ts imports no `node:fs`/`node:path` and never builds a path — a poisoned `storage_key` fails the regex inside FsStorage and is logged, not followed. |
| T-m3v-02 | Denial of Service | purge sweep vs. ingest availability | medium | mitigate | Artifact sweep bounded to `ARTIFACT_BATCH = 100` rows per tick; identity sweep is a single set-based UPDATE; a closure `running` flag skips overlapping ticks; `timer.unref()` plus `clearInterval` on Fastify `onClose` (caps.ts pattern); the whole sweep body is wrapped in try/catch that logs `[watchbug] purge sweep failed` — a purge error can never reject the boot promise, crash the process, or touch request handling. |
| T-m3v-03 | Information Disclosure | purge log lines | medium | mitigate | Log output is restricted to counts, configuration, and incident uuids; `user_id`/`user_name`/`user_email` values are never interpolated into `[watchbug] purge` lines (the destroyed PII must not be re-published into `docker compose logs`). |
| T-m3v-04 | Repudiation | silent retention failure | medium | mitigate | Every non-empty sweep writes `[watchbug] purge: identity=<n> artifacts=<n>` and every failure path (DB error, per-row blob error) logs with the `[watchbug] purge` prefix and the incident uuid — a broken retention job is observable in `docker compose logs api` instead of failing silently, which is exactly the S-2 finding's failure mode. |
| T-m3v-05 | Denial of Service | `WATCHBUG_PURGE_INTERVAL_MINUTES` | low | mitigate | Read through config.ts `readInt` (positive-integer regex, minimum 1): a `0`, negative, or garbage value exits the process at boot naming the variable, so a zero-delay hot loop flushing the DB pool is structurally impossible. |
| T-m3v-06 | Tampering | artifact purge ordering (row vs blob) | medium | mitigate | Blob is deleted BEFORE the row; the row delete runs only after `storage.delete` resolves. Row-first ordering would create a rowless blob that this by-row job can never observe again (WR-03, incidents.ts:296) — an unrecoverable volume leak. On blob failure the row is kept and retried next tick; `FsStorage.delete` is idempotent (`rm --force`), so retries are safe. |
| T-m3v-SC | Tampering | npm/pip/cargo installs | high | mitigate | This plan performs ZERO package installs — no scheduler library, no new dependency of any kind (plain `setInterval` per the analysis guidance).
