## Phase Goal

**As an** end user of a web app, **I want to** compose a complete bug report or plain feedback -- capture or attach an image, annotate it, destructively mask anything sensitive, review it, and file it -- with the editor fetched on gesture and the whole widget UI in English or Spanish, **so that** the developer receives a report they can reproduce and neither the report nor its screenshot ever leaves the developer's own infrastructure.

**This plan's slice:** the lazy annotation editor's frame and its drawing tools -- a fullscreen canvas inside the widget's shadow root, fetched only when `Annotate image` is clicked, where the user can draw freehand, arrows, rectangles and text labels and undo them stroke by stroke. The destructive mask tool lands in 03-06.

<objective>
Replace the `annotator.ts` build-stub with a real hand-rolled canvas editor in the lazy lane, load it on demand with one non-analyzable `import()`, and prove the laziness and the chunk budget rather than assuming them.

D-05 closed `fabric.js` (about 85 KB gz) and `konva` (about 45 KB gz) as over-budget on their own, so the editor is hand-written against `CanvasRenderingContext2D`. C-2's `Annotator` contract is fixed: one flattened working bitmap, vector strokes flattened onto it, masks baked destructively and never undoable, and a single encode sink in core -- which means the editor returns `ImageData` and `MaskPatch[]` and never names the canvas encode API (the `sdk-single-encode-sink` gate counts text, comments included).

The loading mechanism is the other half of the risk. esbuild's `splitting` works for ESM only, so a string-literal `import('./annotator.ts')` is inlined into the IIFE core and the 45 KB tier fails; a specifier routed through a variable survives in both formats (verified on this repo's esbuild 0.28.2), and `import.meta.url` compiles to `undefined` in the IIFE lane, so the base URL comes from `LOADING_SCRIPT_URL` there.

Purpose: this is the only genuinely new code in the phase -- every other "hard" problem (geometry, caps, encode, copy, pointer-free DOM) already exists in the repository and must be reused (R-18). The plan therefore spends its risk budget on the loader, the pointer->bitmap mapping and the laziness proof.

Output: `widget/loader.ts`, a real `annotator.ts` plus `annotator/{canvas-layer,tools,editor-dom}.ts`, `strings.editor.ts`, the annotate-button loading/error states, the e2e harness that can serve and drive the chunk, `ANN-01..04` rows, the `PRF-02` laziness row, the size gate's max-plus-floor rule, and two new static gates.
</objective>

## Flagged assumptions & planner decisions (surfaced, not silent)

- **Lazy-load timing (discretion, decided here).** Fetch on demand at the `Annotate image` click only (UI-SPEC A-2). No prefetch at capture: most reports are never annotated, and a prefetch would make the `PRF-02 lazy` row vacuous. The visible loading state is a 12 px spinner plus `editor.loading` on the disabled button.
- **The lazy lane is `.mjs`.** `import()` always evaluates its target as a module, so the shipped chunk is the ESM twin; the `.js` twin keeps being emitted and the gate now budgets the max of the two (research OQ-5) so neither can drift.
- **`EDITOR_CSS` is appended to the core style element** rather than injected as a second `<style>`: the UI-SPEC forbids a second stylesheet and `adoptedStyleSheets`, and this keeps the CSS bytes in the lazy lane.
- **`widget/loader.ts` type-imports `AnnotatorModule`** from `annotator.ts`; `import type` is erased at build time, and the new `sdk-lazy-lane-purity` rule is written to allow exactly that and nothing more.
- **Stroke width and undo depth (discretion, decided here).** 3 px logical ink scaled into bitmap space; 20-entry undo stack, matching the "~20" note in P3-D-11.
- **The editor's redraw base is the draft's own `ImageData`, mutated in place -- no second bitmap exists.** `AnnotatorOpenOptions.base` IS `draft.image`, and `open()` resolves with that same instance, so the editor, the composer preview source and the redraw base are one buffer (C-2's "exactly one flattened working bitmap", and no offscreen base layer). `createImageBitmap` is deliberately NOT used: an immutable copy held for the session would keep the pre-mask pixels of every mask 03-06 bakes alive in memory, which is exactly the state A-04 forbids -- its release would also depend on `bitmap.close()` running on every exit path. The cost is one `putImageData` per redraw instead of a GPU `drawImage`, paid only on stroke commit (never per pointermove, which draws incrementally onto the canvas), and the memory saved at the 16 MP ceiling is ~64 MB of duplicate bitmap.
- **`maskConfirm` is passed in, not imported.** The four `mask.confirm.*` strings are core keys (03-03, per ROADMAP § Phase 3) resolved through `t()` and handed to `open()`; the lazy lane never value-imports `strings.ts`, so the chunk carries no second dictionary and cannot disagree with core about the active locale.
- **The mask tool button exists in this plan's toolbar but is inert until 03-06.** It is rendered (so the rail layout, `aria-pressed` semantics and i18n keys are complete) and selecting it does nothing yet; 03-06 wires the drag, the bake and the confirm dialog. Recovery rows for it land there, not here.
