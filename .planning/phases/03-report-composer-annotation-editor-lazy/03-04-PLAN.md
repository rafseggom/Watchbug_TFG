## Phase Goal

**As an** end user of a web app, **I want to** compose a complete bug report or plain feedback -- capture or attach an image, annotate it, destructively mask anything sensitive, review it, and file it -- with the editor fetched on gesture and the whole widget UI in English or Spanish, **so that** the developer receives a report they can reproduce and neither the report nor its screenshot ever leaves the developer's own infrastructure.

**This plan's slice:** the two escape hatches the phase promises -- attaching a picture from the device instead of capturing (CAP-02), and filing when capture is impossible (CAP-03). Both land in the image zone of the composer 03-03 built.

<objective>
Give the composer a second `CaptureSource` (a user-picked file) and a degraded state with two real ways forward, and make both reach a real 201.

iOS has no `getDisplayMedia` and Safari's canvas-area cap silently blanks large captures, so a phase that only supports capture has no answer for a whole class of reporters. A-05/H-4/H-5 make `DisplayMediaCapture` -> `ManualFileCapture` a mandatory pair, and P3-D-13 forbids the "silently fall through to a file picker" shortcut: capture failure must be a *visible* state with two explicit choices. The attach path is also where an untrusted file enters the widget, so the client applies the same magic-byte allowlist the server does (PATTERNS §13) instead of trusting the picker's `accept` hint.

Purpose: CAP-02 and CAP-03 are the difference between "works on a desktop demo" and "works for the reporter who has a phone". P3-D-15 also rules that an attachment joins the same annotate/review/send flow, so the attached picture must arrive as `ImageData`, not as a blob -- the single encode sink stays the only producer of encoded bytes.

Output: `capture/manual-file.ts` with `createManualFileCapture()`, `fitToCaps()` exported from `encode.ts`, the composer's attach/replace/reject affordances, the degraded state with `Attach image` and `Continue with text only`, an optional image part in the lane-1 transport, and `CAP-02`/`CAP-03` rows.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user file picker -> widget | an arbitrary file selected by the user (or by a hostile page synthesising a change event on a reachable input) crosses here |
| decoded bitmap -> working ImageData | an oversized or malicious container can exhaust memory before any cap applies |
| text-only draft -> ingest | a submission with no image part must not become a submission with no validation |
| capture failure -> user | a failure must never be silently converted into a file dialog or a blank report |

- **Text-only form shape (discretion, decided here).** The text-only draft is the same composer with the image zone hidden (`data-wb-state="text-only"`), a footer `Attach image` kept as the escape hatch back to an image, and `Review report` unchanged as the primary action. - **No automatic fallback from capture to file picker.** A-05 lists the capture chain in order, but P3-D-13 makes the *user* choose. `ManualFileCapture` is a standalone adapter invoked from the composer, never a wrapper around `DisplayMediaCapture`.
- **Client decode-bomb posture (research A4).** Dimensions are checked on the decoded bitmap rather than by parsing the container header in the browser: the input is user-initiated and lives in a closed shadow root the host cannot reach, and a client-side header parser would duplicate the server's walker for a lower-value boundary. The server's pre-sharp guard remains the control of record.
- **`blankProbe` is deliberately not applied to attachments** (research F6): a mostly-uniform photo is a legitimate report, and rejecting it would be a false negative the user cannot argue with.
