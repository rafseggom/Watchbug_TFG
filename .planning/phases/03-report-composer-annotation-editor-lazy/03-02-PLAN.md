## Phase Goal

**As an** end user of a web app, **I want to** compose a complete bug report or plain feedback -- capture or attach an image, annotate it, destructively mask anything sensitive, review it, and file it -- with the editor fetched on gesture and the whole widget UI in English or Spanish, **so that** the developer receives a report they can reproduce and neither the report nor its screenshot ever leaves the developer's own infrastructure.

**This plan's slice:** the server can accept, normalise and serve **JPEG** -- the third attachment format P3-D-14 locks -- without weakening the PNG/WebP control stack. This is a security-surface change (C-3/C-4), reachable by any direct API caller even though the SDK itself always re-encodes to WebP or PNG before sending.

<objective>
Extend the ingest image stack from PNG+WebP to PNG+WebP+JPEG across every stage, with a total ext->MIME mapping and a mandatory EXIF auto-orient, proven at the artifact level.

Phase 1's stack is binary at four points (`sniff.ts`, `structure.ts`, `guard.ts`, `harden.ts`) and the controller maps "not png" to `image/webp`, so adding a third extension without rewriting those five decisions stores JPEG bytes labelled `image/webp` -- which the CHECK constraint happily accepts and `nosniff` then turns into a broken image in the panel. The storage key grammar is a sixth place (`STORAGE_KEY_REGEX` in `apps/api/src/ports.ts`) that would reject the server's own key.

Purpose: CAP-02 lets an end user attach a phone photo. The client never sends JPEG (the single encode sink emits WebP or PNG), so everything here is the server's own contract -- which is exactly why it must be proven with direct HTTP rows, not through the widget.

Output: `ImageExt` with `jpeg`, a 3-byte magic-byte check, an SOF dimension walker, an explicit structural branch with its rationale, an `autoOrient` + `jpeg()` hardening arm, a single ext->MIME map on both controller call sites, three committed fixtures, and the `JPEG` ingest rows.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client bytes -> `sniffImage` | the only admission decision; the declared `Content-Type` is never consulted |
| header bytes -> `assertDecodeSafe` | attacker-controlled dimensions can trigger a decode bomb if not bounded before sharp |
| submitted container -> stored bytes | only libvips' re-encode may reach storage (polyglot / trailing-data control) |
| stored `content_type` -> response headers | one map decides MIME and filename; a drift here serves JPEG bytes as WebP |
| stored key -> filesystem path | the key grammar is a path-safety check as well as a format check |

## Flagged assumptions & planner decisions (surfaced, not silent)

- **No JPEG structural walker (research A3, MEDIUM confidence, accepted).** `validateStructure` passes JPEG bytes through with a written rationale; the sharp re-encode plus the pre-decode dimension guard are the control.
