## Phase Goal

**As an** end user of a web app, **I want to** compose a complete bug report or plain feedback -- capture or attach an image, annotate it, destructively mask anything sensitive, review it, and file it -- with the editor fetched on gesture and the whole widget UI in English or Spanish, **so that** the developer receives a report they can reproduce and neither the report nor its screenshot ever leaves the developer's own infrastructure.

**This plan's slice:** the ingest surface this phase's reporter needs -- a report with **no screenshot at all** (CAP-03's text-only path) must be storable and safely readable, and the stored-content-type constraint must admit `image/jpeg` (P3-D-14) in **one** reviewable migration. No client code: this is the server-side precondition that makes the degraded composer's "Continue with text only" produce a real 201 instead of a 400.

<objective>
Make the ingest surface able to store a screenshot-less report and to admit `image/jpeg` in the same Drizzle migration, gated by one reviewable checkpoint.

Phase 1's route rejects any submission without an `image` part (`apps/api/src/routes/incidents.ts`, the missing-image guard) and the schema declares `storage_key`/`content_type` `NOT NULL`, so CAP-03's "can still file text-only feedback" cannot pass today -- that is the gap this plan closes, together with P3-D-14's `'image/jpeg'` constraint widening so the phase carries exactly one schema migration instead of two.

Purpose: CAP-03 is a Phase 3 requirement with a server half, and the temptation is to fake it client-side with a placeholder image -- which would hand the developer a screenshot the reporter never took and break the core value ("reproduce the bug from the report"). The honest shape is a nullable screenshot plus a route that says "not found" for it.

Output: a nullable-screenshot schema with a committed `0001` migration, an ingest route that accepts meta-only submissions through the full meta pipeline, a 404 blob route for imageless rows, a purge job that tolerates them, panel tolerance, and `e2e/ingest.spec.ts` rows proving it at the artifact level.
</objective>

## Flagged assumptions & planner decisions (surfaced, not silent)

- **The text-only server half is new work not covered by 03-RESEARCH.md.** The research assumed the ingest route already tolerated an imageless report; it does not (the route rejects a missing `image` part and both columns are `NOT NULL`). Treated as a first-class part of CAP-03 rather than faked client-side.
- **One migration, two concerns.** `0001` carries both the nullable screenshot and the `'image/jpeg'` CHECK widening. Rationale: one reviewable artifact for the phase, both changes are widening-only, and a `CHECK` over a NULL value evaluates to UNKNOWN which passes. The checkpoint offers a `split` option if the owner disagrees.
- **Panel tolerance is in scope.** `ReportDetail.tsx` renders the screenshot unconditionally today, so an imageless row would show a broken image. Only the conditional is added; the Phase 6 detail-view work is untouched.
- **`content_type` stays the single source of MIME truth** (the ext->MIME map is inverted, never duplicated), which is also what 03-02 relies on when it adds the `jpeg` arm.
