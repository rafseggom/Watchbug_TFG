## Phase Goal

**As an** end user of a web app, **I want to** compose a complete bug report or plain feedback -- capture or attach an image, annotate it, destructively mask anything sensitive, review it, and file it -- with the editor fetched on gesture and the whole widget UI in English or Spanish, **so that** the developer receives a report they can reproduce and neither the report nor its screenshot ever leaves the developer's own infrastructure.

**This plan's slice:** the phase's closing accounting -- the ~30 existing rows that assumed the one-gesture send are migrated onto the composer (not deleted), and the two budget requirements (PRF-02, PRF-03) are proven against the real emitted chunks on all three engines.

<objective>
Migrate the whole widget suite onto the composer with one shared helper, then close the size gate on real numbers.

Phase 3 inserts a form between the launcher click and the POST, and nearly every Phase 2 row ends at `Report sent`; the capture-failure rows additionally move from the status panel's failure copy to the degraded composer. That is the single largest schedule item in the phase and the one most likely to be "fixed" by deleting rows or by loosening assertions -- both of which would quietly retire the evidence for PRV-01..03, CAP-04, CAP-05 and WDG-01..05.

Purpose: R-12 says the release gate is one suite plus the size gate. A suite that no longer asserts what it used to assert is worse than a failing one, because it looks green. This plan makes the migration mechanical (one helper, one edit per row family), keeps every assertion, and then re-states the budget on the artifacts that actually ship.

Output: `completeComposer` applied across the suite, the failure rows re-pointed at the degraded composer, the final `scripts/check-size.mjs`, the gate's five rules with an honest sink message, and a full `npm run verify` green on chromium + firefox + webkit.
</objective>

## Flagged assumptions & planner decisions (surfaced, not silent)

- **The migration is one plan on purpose** (research F4): interleaving it with feature work makes the RED/GREEN story unreadable, and a per-row bespoke edit is how assertions get quietly weakened.
- **`completeComposer` deliberately does not wait for `Report sent`.** Callers keep their own terminal assertion, which is what distinguishes a send that landed from one that merely navigated.
- **The failure rows changed surface, not meaning.** They still assert "nothing was posted before the user chose"; only the DOM they assert on moved from the status panel to the degraded composer.
- **Measured baseline to beat (2026-10-28):** core 9.3 KB, lazy 0.3 KB, runtime 10.0 KB. The editor plus the English/Spanish core copy must still land under 45 / 25 / 80; if the lazy lane exceeds 25 KB the fix is to cut editor bytes (icon paths, CSS shorthand), never to raise the tier.
