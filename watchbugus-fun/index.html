The honest version

What the hell is Watchbug? 🐛

It is a bug-reporting tool, like the little "Send feedback" button every SaaS app has — except it runs on your server, and the screenshot is cleaned on the user's machine before it is sent anywhere. Not in a dashboard. Not in a cloud bucket. On the canvas, before encoding. That distinction is the whole product.

🔌

One <script> tag

Drop <script src="/watchbug.js" async></script> in your page and call Watchbug.init(). No npm install, no build step, no React context provider you have to thread through 14 files.

🏠

Self-hosted by default

API, panel and PostgreSQL, all in one docker-compose.yml. Your reports live in your database and your filesystem volume. There is no "our cloud" to opt out of.

🖤

Destructive masking

Passwords, tokens, card numbers and anything marked data-watchbug-sensitive get a flat opaque fill painted over the ImageData. The original pixels are gone. No CSS overlay. No blur to un-blur.

🧾

Context, not vibes

Every report can carry console logs, environment metadata, the URL, the viewport and the annotation layer. Enough to reproduce, small enough to read on a laptop.

Reality check: this page is a parody for a university project. The product above is real; the hotdogs, the prize wheel and Steve are not. Steve is a stock character and, frankly, a liability.

Three steps, no mystery

How it works

The flow is deliberately boring, because "boring" is what makes a bug report trustworthy.

  1. The user clicks the floating bug

    The widget opens in a closed Shadow DOM, so your CSS cannot break it and its CSS cannot break you. The user captures the current tab through the browser's own screen-share picker.

  2. They annotate, then Watchbug masks

    Arrows, boxes, text. Then the redactor walks the pixels: password fields, credential patterns and data-watchbug-sensitive nodes are filled with solid black inside the canvas data. Only then is the image encoded to WebP or PNG.

  3. You get a report you can act on

    A multipart POST lands on your API: image, annotation layer, console logs, environment. It is stored in your PostgreSQL and your volume, and rendered inert in your admin panel. No third party in the loop.

What Watchbug does on capture:

Questions people actually ask

FAQ (answers included)

Is this a real product or a joke?
Both, awkwardly. Watchbug is the real project this parody site is promoting: a self-hosted bug-reporting SDK with destructive screenshot masking. The site around it is a joke. The repository is not.
Does it really need only one script tag?
Yes: one async script for the core, plus a lazy chunk for the annotation editor when the user actually opens it. The core stays small because it refuses to ship a framework to draw a rectangle.
What exactly gets masked?
Password inputs, values that look like credentials/tokens/card numbers, and any element you mark with data-watchbug-sensitive. The mask is a flat opaque fill written into the pixel buffer before encoding. Blur is deliberately not offered: it is partly invertible.
Can Watchbug read my users' cookies or tokens?
No, and that is a hard rule, not a setting. The SDK never reads cookies, local/session storage, auth headers or bearer tokens. The only thing it sends that identifies your project is the public, write-only project_key.
What do I need to run it?
Docker and a domain. docker compose up gives you the API, the admin panel and PostgreSQL. Configuration is environment variables; there are no secrets in the repository.
Why is the admin panel so ugly here?
Because this is the marketing parody, not the panel. The panel is a calm, boring triage screen. Calm and boring is a compliment in ops tooling.
Who is Steve?
Steve from Accounting is a fictional "senior bug consultant" invented for this parody. He knows nothing about bugs. He will still call you.
